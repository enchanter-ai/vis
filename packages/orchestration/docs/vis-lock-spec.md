# `.vis-lock` — Schema

The `.vis-lock` file is the resolved-state snapshot generated by
`scripts/bootstrap.sh` / `scripts/bootstrap.ps1` in every `@enchanter-ai` sibling plugin. It
pairs with `.vis-versions` (the manifest of intent — pinned package specs) the way
`package-lock.json` pairs with `package.json`.

Per the s2.0 4-layer recommendation:

- **Layer 1 (Bootstrap)** writes this file.
- **Layer 2 (SessionStart hook)** reads it and compares to current state; fail-loud on drift.
- **Layer 3 (CI verify)** runs `./scripts/bootstrap.sh --verify` which is hash-coverage all-or-nothing against this file.

> **This document describes schema v2** (`lock_version: 2`), adopted for WIX-INSTALL-002. Schema
> v1 (no `lock_version`/`mode` field, a single top-level `vis_commit`) is documented at the
> bottom for historical reference; a v1 lock is rejected by a v2-aware `bootstrap.sh` with
> `"lock is stale or wrong-schema (missing 'mode:')"`.

## What changed from v1, and why

v1's `--verify` compared the sibling's live checked-out `HEAD` (`vis_commit`) against the lock,
and separately compared each package's re-resolved tag against the lock's `tag_commit` — but the
**content it hashed came from the sibling's live working tree**, not from the pinned commit. A
lock could therefore claim `tag_commit: <X>` while every hashed conduct file actually came from
whatever the sibling happened to have checked out — a recorded tag/version describing different
content than what was imported. v2 fixes this at the root: pinned mode never reads file content
from the sibling's working tree at all.

## Contract

- **Generated, not edited.** Every line is auto-emitted by `bootstrap.sh` / `bootstrap.ps1`.
- **Committed to the plugin repo.** Like `package-lock.json`, the lock is a tracked artifact — the sibling's identity includes the resolved vis state.
- **All-or-nothing.** A `.vis-lock` that is missing entries for any `@`-import a plugin actually
  loads (its `CLAUDE.md`, and every plugin agent/skill that references vis conduct directly) is
  an error, not a degraded state. Bootstrap aborts; CI fails. `--verify` additionally rejects an
  entry set that has anything **extra** — an unknown package block or conduct-file entry the
  current `.vis-versions`/imports don't expect — not just anything missing.
- **Two modes, `pinned` (default) and `floating` (explicit opt-in only, never CI):**
  - **`pinned`** resolves each package's tag to an exact commit and reads every imported file's
    content via read-only `git show <tag_commit>:<path>` against the sibling's object database —
    never the sibling's checked-out working tree, index or HEAD. The sibling is only ever read
    from (tag refs, blob content); it is never fetched, checked out, reset or otherwise mutated
    by bootstrap or `--verify`. A tag that cannot be resolved **locally** (bootstrap does not
    fetch) fails loud, naming the missing tag and telling the operator to fetch it or ask the vis
    owner to cut it — never "bump `.vis-versions`" as the primary remedy, since the usual cause
    is that the release hasn't happened yet, not that the pin is wrong.
  - **`floating`** reads from the sibling's live working tree (the pre-v2 behavior), records
    `vis_head` instead of per-package `tag`/`tag_commit`, and its own `--verify` compares that
    against the sibling's current HEAD. Never the default; never used by CI; exists only as a
    named, explicit local-dev convenience.
- **`--verify` re-derives from the pin, it does not just re-hash the local cache.** For pinned
  mode, verify (a) re-resolves every package's tag to a commit from the sibling's *current local*
  refs (still read-only — no fetch), (b) re-reads every expected file's content straight from
  that resolved commit via `git show` (independent of whatever is sitting in the materialized
  cache), and (c) requires all three of {declared `.vis-versions`, the lock file, the freshly
  re-derived pin content, and the on-disk materialized cache} to agree — on package identity
  (`version`, `tag`, `tag_commit` all checked, not just `tag_commit`), on the schema
  (`lock_version` must equal the version this bootstrap build understands, exactly — `99` or any
  other value fails), and on the exact conduct-file entry set (no extra, no missing). A forged
  `version:`/`tag:` line, a `lock_version` that doesn't match, an extra or missing package block
  or conduct-file entry, or a lock+cache pair that is internally consistent with each other but
  does not match what the *pin itself currently contains* — all fail non-zero, each with its own
  named cause.
- **`--verify` parses the lock strictly against the schema**, not just well-enough to find the
  fields it wants: a *duplicate* package block or conduct-file entry (even one with a
  plausible-looking forged `tag_commit`/`sha1`) and an *unknown* key anywhere (top level, inside a
  package block, or inside a conduct-file entry) are both refused, not silently ignored.
- **Every `@`-import in the consuming repo is discovered by resolution, not by matching a fixed
  literal path string.** A plugin agent/skill file nested several directories deep may legitimately
  need `@../../../.vis-cache/vis/...` (more `../` than a file at the repo root) — bootstrap resolves
  each `@<relpath>` token relative to the file that contains it and only then classifies it as a
  covered cache import, an unpinned raw-sibling import (hard error), or unrelated. Directory
  exclusions (`.git`, `.vis-cache`, `state`, `node_modules`) apply to path components *relative to
  the repo root* only — never as a substring match against the full filesystem path, which would
  also match an ancestor directory of the repo itself and silently exclude everything.

## Shape

```yaml
# .vis-lock - auto-generated by scripts/bootstrap.sh
# Do not edit by hand. Run ./scripts/bootstrap.sh to refresh.
lock_version: 2
mode: pinned
resolved_at: 2026-05-12T14:33:07Z
packages:
  core:
    version: v0.7.0
    tag: enchanter-core--v0.7.0
    tag_commit: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  skills:
    version: v0.7.0
    tag: enchanter-skills--v0.7.0
    tag_commit: bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
  web:
    version: v0.7.0
    tag: enchanter-web--v0.7.0
    tag_commit: cccccccccccccccccccccccccccccccccccccccc
  orchestration:
    version: v0.7.0
    tag: enchanter-orchestration--v0.7.0
    tag_commit: dddddddddddddddddddddddddddddddddddddddd
conduct_files:
  - path: packages/core/conduct/discipline.md
    sha1: 1234567890abcdef1234567890abcdef12345678
  - path: packages/core/conduct/context.md
    sha1: 234567890abcdef1234567890abcdef123456789a
  # ... one entry per vis conduct file the plugin actually loads (CLAUDE.md
  #     @-imports plus any plugin agent/skill that references vis directly)
```

Floating mode's shape is the same except `packages` is replaced by a single `vis_head: <sha>`
line (no per-package block, since there is no per-package pin in floating mode).

## Field-by-field (pinned mode)

| Field | Type | Source | Used by |
|---|---|---|---|
| `lock_version` | integer | fixed by the bootstrap script version that wrote it | `--verify` requires an exact match to the schema this build understands; any other value (including a forged/future one) fails loud, named |
| `mode` | `pinned` \| `floating` | which mode wrote the lock | `--verify` requires this to match the mode it was invoked with |
| `resolved_at` | ISO 8601 UTC | bootstrap timestamp | Diagnostic only; not compared |
| `packages.<name>.version` | string | parsed from `.vis-versions` | `--verify` compares against `.vis-versions`, not diagnostic-only in v2 |
| `packages.<name>.tag` | string | `enchanter-<name>--v<version>` | `--verify` compares against the tag name it would itself construct from `.vis-versions` |
| `packages.<name>.tag_commit` | git SHA | `git -C ../vis rev-list -n 1 refs/tags/enchanter-<name>--v<version>` (local refs only, no fetch) | `--verify` re-resolves and compares; mismatch = pin moved, retagged, or `.vis-versions` changed without re-bootstrap |
| `conduct_files[].path` | string | extracted from every vis `@`-import the plugin loads | `--verify` requires the exact set: missing OR extra is an error |
| `conduct_files[].sha1` | hex (40 char) | `sha1sum` of the file's content **as read from the pinned commit** (`git show <tag_commit>:<path>`) at bootstrap time | `--verify` re-derives this fresh from the pin (not just re-hashing the cache) and compares against both the lock's own value and the materialized cache's current content |

## Allowed mutations

Only `scripts/bootstrap.sh` / `scripts/bootstrap.ps1` mutate this file. Two trigger paths:

1. **Explicit:** developer runs `./scripts/bootstrap.sh` after updating `.vis-versions`. Lock is rewritten with new resolved state.
2. **CI sanity:** CI runs `./scripts/bootstrap.sh` (no `--verify`) and asserts the resulting lock matches the committed lock byte-for-byte (excluding `resolved_at`). If CI's regenerated lock differs from what's checked in, the PR is failed with the message `".vis-lock is out of sync with .vis-versions"`.

Hand-editing this file, or any tool other than the bootstrap scripts writing it, is a contract
violation. **A PowerShell-written lock must be byte-identical to a bash-written one** (ASCII
header punctuation, byte-order-not-culture sort of entries, LF line endings, no BOM in the lock
file itself) — a lock's origin (which script/platform wrote it) must never be observable by
diffing it, since it is committed to a shared repo other platforms also verify against.

## Failure-mode mapping

| Drift type | Detected by | Output |
|---|---|---|
| Lock missing | Hook + `--verify` | `"vis not bootstrapped — run ./scripts/bootstrap.sh"` |
| Vis sibling missing | Hook + `--verify` | `"vis sibling missing — run ./scripts/bootstrap.sh"` |
| Lock missing `mode:` or `lock_version:` entirely (e.g. a v1 lock) | `--verify` | `"lock is stale or wrong-schema (missing 'mode:' or 'lock_version:')"` |
| `lock_version:` present but ≠ the schema this build understands (e.g. `99`) | `--verify` | `"lock_version mismatch: lock says <X>, this bootstrap understands <Y>"` |
| Duplicate or unknown key anywhere in the lock (top level, a package block, or a conduct_files entry) | `--verify` | named per case: `"duplicate top-level key"` / `"duplicate package block"` / `"duplicate conduct_files entry"` / `"unknown top-level key"` / `"unknown key in package '<pkg>' block"` / `"unknown key in conduct_files entry '<path>'"` |
| Lock `mode:` ≠ requested mode | `--verify` | `"lock mode mismatch: lock says <X>, verify requested <Y>"` |
| Pinned tag not resolvable in the sibling's **local** refs | bootstrap + `--verify` | `"vis tag <tag> not found locally - fetch it (git -C ../vis fetch --tags) or ask the vis owner to cut it"` — never fetched automatically |
| `packages.<pkg>.{version,tag,tag_commit}` ≠ re-resolved from `.vis-versions` + the sibling's local tag refs | `--verify` | `"package <pkg>: recorded tag/version no longer resolves to the same content"` |
| Extra/missing package block or conduct-file entry vs. the current expected set | `--verify` | named per entry: `"unexpected package block"` / `"unexpected conduct-file entry"` / `"conduct file not in lock"` |
| `conduct_files[].sha1` ≠ content freshly re-derived from the pin, or ≠ the materialized cache's current content | `--verify` | `"conduct file <path> modified in the materialized cache since bootstrap"` (cache tampered) or `"conduct file <path>: lock/pin content mismatch"` (lock forged or lock+cache copied from another commit) |
| Conduct file referenced by a plugin but absent from the lock | bootstrap (refuses to write) | `"import resolves to missing file: <path>"` |
| Floating mode: `vis_head` ≠ sibling's current live HEAD | Hook + `--verify` (floating mode only) | `"vis drift (floating mode): lock says <X>, checkout is <Y>"` |

## Versioning

Backward-incompatible changes (rename a top-level field, change `sha1` to `sha256`, add a
required field) require a `lock_version` bump and a coordinated update across `bootstrap.sh`,
`bootstrap.ps1`, the SessionStart hook, and CI. Additive optional fields do not require a version
bump but should be documented here first. This document, at v2, supersedes v1 below (kept for
historical reference only — do not write a v1-shaped lock).

## Cross-vendor analogues

Lock-file pattern is well-precedented:

- **`package-lock.json`** (npm) — same role: manifest intent + resolved state, fail loud on `npm ci` if they disagree.
- **`Cargo.lock`** (Rust) — same: lock is the source of truth for actual versions installed; manifest is the constraint.
- **`go.sum`** (Go) — hash-coverage analogue. `go mod verify` mismatch produces a `SECURITY ERROR` and non-zero exit.
- **`requirements.txt`** with `--require-hashes` (pip) — partial-coverage is an error per pip docs.

`.vis-lock` is the @enchanter-ai analogue. It exists because @-imports without it fail silently (see Brief Pattern A.3, Git submodules).
